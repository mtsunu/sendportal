# Architecture Research

**Domain:** Laravel 11 application compatibility release (PHP 8.4, Composer, and CI)
**Researched:** 2026-07-22
**Confidence:** MEDIUM

## Standard Architecture

### System Overview

```text
┌─────────────────────────────────────────────────────────────────────┐
│ Source-of-truth dependency boundary                                  │
│ composer.json ── constraint policy ──> composer.lock (committed)     │
└───────────────────────────────┬─────────────────────────────────────┘
                                │ composer install on the real runtime
                                v
┌─────────────────────────────────────────────────────────────────────┐
│ Laravel application boundary — unchanged product architecture        │
│ artisan / public/index.php -> bootstrap/app.php -> providers/routes  │
│                                │                                    │
│                                └-> AppServiceProvider -> SendPortal  │
│                                    Core resolver and UI hooks        │
└───────────────────────────────┬─────────────────────────────────────┘
                                │ package discovery, boot, migrations
                                v
┌─────────────────────────────────────────────────────────────────────┐
│ Verification boundary                                                │
│ Composer validation/platform/audit -> boot smoke -> PHPUnit          │
│ PHP 8.2 / 8.3 / 8.4                 MySQL 5.7 and PostgreSQL         │
└─────────────────────────────────────────────────────────────────────┘
```

This is a dependency-and-verification milestone, not an application redesign. The host must retain its current responsibility for identity, workspace tenancy, setup, and extension fragments. `mettle/sendportal-core` remains the owner of newsletter/campaign/subscriber behaviour and is still composed through the existing route registrars and `AppServiceProvider` resolvers.

### Component Responsibilities

| Component | Responsibility | Typical implementation in this repository |
|-----------|----------------|--------------------------------------------|
| Composer manifest | Declares the supported PHP interval and direct package compatibility policy. It must be truthful, not an escape hatch. | `composer.json`: express PHP 8.2–8.x as `^8.2`; make only dependency-bound changes needed for a solvable graph; never add `--ignore-platform-req*` or a fake platform override. |
| Dependency lock | Pins the solved project dependency graph so developer, CI, and operator installations use identical package versions. | New committed `composer.lock`, generated by a deliberate update on real PHP 8.4 after manifest changes. |
| Laravel boot and package composition | Autoloads providers, discovers packages, configures the workspace resolver, and registers host plus Core routes. | Leave `bootstrap/app.php`, `config/app.php`, `app/Providers/AppServiceProvider.php`, `routes/web.php`, and `routes/api.php` unchanged unless a real PHP-8.4 failure identifies one. |
| Test harness | Boots the same application and runs migrations for host and package-integrated feature tests. | `phpunit.xml.dist`, `tests/TestCase.php`, and existing feature tests; each test setup invokes `artisan migrate`. |
| CI matrix | Runs the frozen graph on each supported PHP runtime and both already-supported database engines. | `.github/workflows/ci.yml`: add the 8.4 runner image to the existing container matrix; preserve MySQL and PostgreSQL service aliases. |
| Dependency safety gate | Detects advisories without making an incompatible advisory metapackage part of the resolution graph. | Run `composer audit --locked` in CI (and document it for release work) after replacing the blocking Roave constraint with this equivalent gate. |

## Recommended Project Structure

```text
composer.json                         # PHP/support constraints and direct dependencies
composer.lock                         # resolved, reviewed application graph (new and committed)
.github/workflows/ci.yml              # PHP runtime × database verification matrix
phpunit.xml.dist                      # common test environment; existing DB credentials retained
bootstrap/app.php                     # existing Laravel application bootstrap; no compatibility fork
config/app.php                        # existing provider registry
app/Providers/AppServiceProvider.php  # existing SendPortal Core workspace/UI integration
routes/
├── web.php                            # existing host + Core web route delegation
└── api.php                            # existing host + Core API route delegation
tests/                                 # existing host and integration feature coverage
```

### Structure Rationale

- **`composer.json` and `composer.lock`:** treat these as one versioned contract. The manifest describes supported versions; the lock records the exact graph that demonstrated that claim. This is a project application, so Composer explicitly recommends committing the lockfile.
- **`.github/workflows/ci.yml`:** owns runtime coverage only. It should not recreate application configuration or move database setup into production code.
- **Laravel/Core integration files:** are assertion targets, not planned edit targets. A successful boot test proves the locked graph still loads the Core package through the existing package-discovery/provider/route boundary.
- **`tests/`:** remain the behavioural proof. The suite already exercises host workspace operations while using real MySQL and PostgreSQL services; expanding it solely for a speculative PHP syntax change would add noise.

## Architectural Patterns

### Pattern 1: Locked Application Dependency Graph

**What:** Resolve once with an intentional `composer update` and commit `composer.lock`; install with `composer install` everywhere else.

**When to use:** Always for this deployable SendPortal host application. Composer documents `update` as the command that resolves constraints and writes the lock, and `install` as the command that consumes it reproducibly.

**Trade-offs:** A lock requires an explicit update/review when dependency policy changes, but prevents invisible package drift between developers, CI, and operators. That is the correct trade-off for a compatibility release.

```bash
# Resolution workstation/CI preparation, running real PHP 8.4.
composer validate --strict
composer update --with-all-dependencies
composer check-platform-reqs

# Review and commit both manifest and resolved graph.
composer audit --locked

# Ordinary developer, CI, and deployment path.
composer install --no-interaction --prefer-dist
```

Use `^8.2` for the root PHP requirement rather than an enumerated `^8.2|^8.3|^8.4`: Composer caret semantics already allow every PHP 8.x release from 8.2 up to, but not including, 9.0. The lock/CI matrix then proves the actual supported points. Do not set `config.platform.php` to 8.4 as a workaround; it would hide failures on the runtime that actually executes the application.

The current `roave/security-advisories: dev-master` is a graph participant and is known to conflict with Laravel 11's `illuminate/mail` path. Replace that package-level blocker only with an explicit CI `composer audit --locked` gate (and keep it failing by default); Composer's audit command checks the lock graph against Packagist advisory data. Do not suppress platform or security checks merely to generate a lock.

### Pattern 2: Preserve the Host/Package Boundary

**What:** Validate compatibility by booting the unmodified Laravel host, which discovers `mettle/sendportal-core`, runs the existing `AppServiceProvider` workspace/UI callbacks, and mounts the existing Core route registrations.

**When to use:** During and after dependency resolution. A package upgrade can be dependency-valid but still fail during provider discovery, container resolution, route registration, or migration boot.

**Trade-offs:** A boot smoke test is intentionally broad but shallow. It catches integration failures early; PHPUnit remains necessary for workspace tenancy and database-specific behaviour.

```bash
# Run after a normal (scripts enabled) composer install.
php artisan package:discover --ansi
php artisan about --no-ansi
php artisan route:list --no-ansi
```

These commands must run before PHPUnit in the PHP 8.4 path. `about` forces Laravel/provider boot, while `route:list` forces registration of both host and SendPortal Core routes. Neither command needs new product behaviour or a replacement service provider.

### Pattern 3: Runtime × Database Matrix With One Frozen Graph

**What:** Install the committed lockfile under each supported PHP runtime, then execute the suite against both databases. The existing container job topology is suitable: a job container reaches its service containers by the `mysql` and `postgres` service names.

**When to use:** Every push and pull request, after the lockfile exists.

**Trade-offs:** Three PHP versions times two database runs is six suite executions, increasing CI time. It is justified because PHP compatibility and database driver behaviour are independent risks; collapsing to only PHP 8.4 or only one database would weaken an existing guarantee.

```yaml
strategy:
  matrix:
    container:
      - kirschbaumdevelopment/laravel-test-runner:8.2
      - kirschbaumdevelopment/laravel-test-runner:8.3
      - kirschbaumdevelopment/laravel-test-runner:8.4
```

Keep the current `mysql:5.7` and PostgreSQL service definitions and execute the same suite with `DB_CONNECTION`/`DB_HOST` set for each. The published `laravel-test-runner:8.4` tag allows the minimal matrix expansion; a migration to a different CI PHP-setup action is not necessary for this milestone.

## Data Flow

### Compatibility-Release Flow

```text
composer.json change
        |
        v
PHP 8.4 composer update (normal platform checks)
        |
        +-- unsatisfiable -> adjust direct constraints/security mechanism, retry
        |
        v
composer.lock (review + commit)
        |
        v
each CI runtime: composer install
        |
        +-- validate / check-platform-reqs / audit --locked
        |
        v
Laravel package discovery -> provider boot -> Core route registration
        |
        v
PHPUnit with mysql service -> PHPUnit with postgres service
```

### Existing Application Request Flow (Preserved)

```text
HTTP / Artisan
    -> bootstrap/app.php
    -> configured Laravel providers
    -> AppServiceProvider workspace-id and layout resolvers
    -> host routes + Sendportal::webRoutes()/apiRoutes()
    -> SendPortal Core tenant-scoped feature layer
    -> configured MySQL or PostgreSQL persistence
```

The compatibility flow feeds this request flow only by choosing its vendor graph. It must not bypass `RequireWorkspace`, duplicate Core routes/models, or alter the host's workspace resolver. The existing feature suite's migrations and `RefreshDatabase` usage make a database run a meaningful integration check rather than a syntax-only test.

## Build Order and Minimal File-Level Changes

1. **Make the manifest truthful and remove the blocker.** Update `composer.json` to cover PHP 8.4 via `^8.2` (or an equivalent range), revise only packages whose constraints prevent the Laravel 11 graph, and remove `roave/security-advisories` only as part of adding an audit gate. Do not change `bootstrap/`, `app/`, `routes/`, migrations, or application tests in this step.
2. **Resolve and freeze on PHP 8.4.** Run `composer validate --strict`, then a normal `composer update --with-all-dependencies` under PHP 8.4. Inspect changes, run `check-platform-reqs`, and commit the generated `composer.lock` with `composer.json`. This ordering proves that PHP 8.4 is not being ignored during resolution.
3. **Prove the host/Core boot boundary.** From the locked graph, use normal `composer install` with scripts enabled, perform package discovery plus `artisan about` and `route:list`. Only if one of those fails should a minimal, evidence-led adjustment be made to package constraints or application code.
4. **Extend the existing CI matrix.** Add `kirschbaumdevelopment/laravel-test-runner:8.4` in `.github/workflows/ci.yml`; use the committed lock with `composer install`, add `composer validate --strict`, `composer check-platform-reqs`, and `composer audit --locked`, then retain both current PHPUnit invocations unchanged. Ensure package-discovery/boot smoke is present before tests if CI continues to install with `--no-scripts`; preferably remove `--no-scripts` so CI verifies the operator's standard install path.
5. **Record supported-install evidence.** Optionally update `README.md` only if it currently states the older PHP range or install command; do not create a new runtime abstraction, test configuration, database service, or documentation subsystem.

| File | Change | Why it is the smallest correct boundary |
|------|--------|------------------------------------------|
| `composer.json` | PHP range, exact direct-constraint adjustments, security-audit replacement policy. | The only place product dependency intent belongs. |
| `composer.lock` | Add and commit generated graph. | Required for reproducible installs; no handwritten edits. |
| `.github/workflows/ci.yml` | Add PHP 8.4 image and integrity/boot/audit gates; retain DB services and test commands. | Extends rather than replaces existing compatibility coverage. |
| `README.md` (conditional) | Correct PHP support/install wording if present. | Keeps operator expectations aligned without scope expansion. |
| `app/`, `routes/`, `bootstrap/`, `config/`, `tests/` | No planned change. | Their existing behaviour is what the locked graph must preserve. |

## Scaling Considerations

| Scale | Architecture Adjustments |
|-------|--------------------------|
| This compatibility milestone | One lockfile plus a 3×2 runtime/database execution matrix is sufficient. |
| More supported PHP/database targets | Factor CI into explicit `php` and `database` matrix axes and add `fail-fast: false`; retain the same single lockfile. |
| Frequent dependency maintenance | Add a scheduled dependency-audit/update proposal workflow, but keep merged application CI on `composer install` so unreviewed graph changes never reach a release. |

### Scaling Priorities

1. **First bottleneck: nondeterministic fresh resolution.** Fix with the committed lockfile and `composer install`; never use fresh `composer update` as normal CI/deploy behaviour.
2. **Second bottleneck: opaque matrix failures.** Keep job names showing the PHP container and separate the MySQL/PostgreSQL test steps so failures identify the runtime/driver combination immediately.

## Anti-Patterns

### Anti-Pattern 1: Ignoring PHP Platform Requirements

**What people do:** Run `composer update` or `install` with `--ignore-platform-reqs`, pin `config.platform.php` to an older version, or loosen the root range without running under PHP 8.4.

**Why it's wrong:** Composer's PHP platform package is the mechanism that exposes incompatible dependency constraints. Bypassing it creates an install that can fail at boot or in production.

**Do this instead:** Resolve and run the graph on real PHP 8.4, then use `composer check-platform-reqs` against the installed packages.

### Anti-Pattern 2: Treating a Security Metapackage Conflict as a Reason to Drop Security Checks

**What people do:** Delete `roave/security-advisories` to make resolution succeed and add no replacement.

**Why it's wrong:** The graph becomes installable but loses the dependency-safety signal explicitly required by the milestone.

**Do this instead:** Make `composer audit --locked` a failing CI step. Review any necessary, scoped audit exceptions with a documented reason; do not set broad ignore or no-blocking flags.

### Anti-Pattern 3: Rewriting CI or Core Integration for a Runtime Upgrade

**What people do:** Replace the CI topology, move SendPortal Core routes into host controllers, or modify tenancy code before evidence of an incompatibility.

**Why it's wrong:** It bundles architecture risk with a dependency constraint change and makes compatibility regressions harder to isolate.

**Do this instead:** Add the 8.4 test image to the current matrix, keep service aliases, and use boot plus existing feature tests to identify the specific package or host defect, if any.

## Integration Points

### External Services

| Service | Integration Pattern | Notes |
|---------|---------------------|-------|
| Packagist/Composer | Resolve once under PHP 8.4; install the committed lock in normal paths; audit the lock in CI. | Composer documents `composer audit` as checking advisories through Packagist's advisory data. |
| GitHub Actions service containers | The PHP job container connects to `mysql` and `postgres` by service name. | GitHub creates fresh service containers per job and removes them when it completes; this matches the current workflow. |
| MySQL 5.7 and PostgreSQL | Existing PHPUnit processes run with `DB_HOST=mysql`/`postgres` and the shared test credentials in `phpunit.xml.dist`. | Preserve current versions unless an actual PHP-8.4 test failure requires database research; database upgrade is outside this milestone. |
| `mettle/sendportal-core` | Composer package discovery and Laravel provider/route composition. | Validate with provider boot and `route:list`; do not vendor or fork the package in this repository. |

### Internal Boundaries

| Boundary | Communication | Notes |
|----------|---------------|-------|
| `composer.json` ↔ `composer.lock` | Constraint resolution then exact version lock. | Both change in one reviewed compatibility commit. |
| CI ↔ lockfile | `composer install` consumes the lock under every PHP runtime. | A matrix install failure is useful evidence that a locked package violates a declared supported runtime. |
| Laravel host ↔ SendPortal Core | Package discovery, providers, facade callbacks, and route registrars. | Keep `AppServiceProvider` and route delegation unchanged; boot is the integration assertion. |
| PHPUnit ↔ database services | Laravel configuration from `phpunit.xml.dist` plus per-step DB environment. | The suite migrates each engine and preserves host/Core behavioural coverage. |
