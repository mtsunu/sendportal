### CRUD interaction contract

- **Create:** `Add Sender` is visible to every authenticated member with an active workspace. It opens the create form. The form requires Label, From Name, and From Email; submit uses `Save Sender`. On success, redirect back to Senders with the success alert and the new row visible.
- **Read:** The Senders navigation item is visible to every authenticated member with an active workspace and has the active state on `/senders*`. The list contains only records from the current workspace. No creator/owner column or owner-only affordance is shown because senders are shared workspace records.
- **Edit:** Each row has `Edit Sender`; the edit form is prefilled with all three values and uses `Save Changes`. On success, return to the list with the updated values and success alert. Any sender ID that is not in the current workspace resolves to the standard 404 response, not an authorization explanation.
- **Delete:** Each row has `Delete Sender`, visually subordinate to the primary action and styled destructive. Require the documented confirmation before DELETE. On confirmation, remove the row and show the success alert; if it was the last row, show the empty state. Cross-workspace IDs remain 404.
- **Authorization visibility:** Never hide sender actions from active-workspace members based on role; every active-workspace member can create, read, edit, and delete every sender in that workspace. Users without an active workspace do not reach the page and receive the existing workspace-required 404 behavior.
- **Feedback:** Render session success/error alerts near the top of the content area, before the cards. Preserve server-side validation errors inline and keep the form values. Do not use toast-only feedback.
